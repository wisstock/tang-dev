# AGENTS.md — Sipeed Tang Nano 9K: open FPGA stack on macOS

Open-source development flow for the Sipeed Tang Nano 9K (Gowin GW1NR-LV9QN88PC6/I5, family GW1N-9C) on Apple Silicon Macs: lint, cocotb simulation, Yosys → nextpnr-himbaechel → gowin_pack, programming with openFPGALoader. User documentation: `README.md`, `FPGA_INTRO.md`.

## Roles

- **Agent:** tools in `.tools/`, project files and designs in `demo/`, lint, simulation, build, diagnostics, documentation.
- **User:** connecting boards, the macOS "Allow accessory" dialog, any command that accesses the board, anything outside the project folder, any git operation other than reading.
- When unsure whose action it is, treat it as the user's and ask.

## Hard rules

1. Write only inside the project folder. Tools go to `.tools/`, not `~/.local`, `/opt` or `/usr/local`.
2. Do not edit `~/.zshrc`, `~/.zprofile`, `~/.bashrc` or other shell configs. `Makefile` sets `PATH`.
3. No `sudo`, `kextunload`/`kmutil`, `softwareupdate`, `xattr`, no changes to system settings or drivers.
4. Do not change `.claude/`, `AGENTS.md`, `CLAUDE.md` without a direct request from the user.
5. Every command that accesses the board (`openFPGALoader`, `make detect|flash-*`) runs only after an explicit "yes" in chat for **this** step. One approval does not carry over to later steps. Run board commands only as `make <target> [DEMO=…]` or `openFPGALoader …` (full path is fine) so the `ask`/sandbox rules in `.claude/settings.json` apply.
6. Writing the board flash (`make flash-perm`, `openFPGALoader -f`) needs a separate approval and an existing flash backup (see "Flash backup").
7. Do not bypass the sandbox: do not move board commands into scripts, `bash -c`, aliases or other Makefile targets.
8. Do not download or install tools: the toolchain is the OSS CAD Suite archive pinned in `tools.lock`. Network only for board reference data from already allowed domains (`github.com`, `api.github.com`), after telling the user what and why. New domains only after explanation and approval.
9. Git is read-only (`git status`, `git log`, `git diff`, `git show`). No `add`, `commit`, `branch`, `checkout`, `stash`, `reset`, `tag`, `push`, etc.
10. All comments in code and project files are in English. `README.md` and `FPGA_INTRO.md` are bilingual (English, Ukrainian) and concise; they describe the stack for people and never mention agent settings (`AGENTS.md`, `.claude/`, hooks, sandbox).
11. For a new task: a short numbered plan first, a brief report after each stage, then wait for instructions.

## When to stop and ask

- Any USB access error (`unable to claim usb device`, `No JTAG chain found`, `Access denied`, `device not found`) — describe the diagnosis and options, change nothing in the system.
- A need to write outside the project or to use a new network domain.
- A checksum mismatch or a need for a different tool release.
- A board pin or electrical parameter not confirmed by a source.
- Any lint, test or build result that differs from the "Status" table.
- Board behaviour that differs from what the design should do — first check the expectation against the code, then look for the cause in the design or pins.

## Commands

Targets and variables are described in `README.md` ("Make targets", "Without make"). For the agent:

- **Board targets** `make detect`, `make flash-sram`, `make flash-perm` (and any `openFPGALoader` call): run outside the sandbox, ask every time; `flash-perm` / `-f` needs a separate approval (rules 5–6).
- **Everything else** (`check-tools`, `demos`, `lint`, `sim`, `build`, `clean`, `clean-all`): sandboxed, no approval needed.
- `make waves` (gtkwave) is run by the user: it writes to `~/.config`.
- `make check-tools` must end with `check-tools: OK` before any lint/sim/build work on a new machine and after any tool change. It does not execute `openFPGALoader` (rule 7), only checks that the binary exists.
- Makefile conventions: `OSS_CAD ?= $(CURDIR)/.tools/oss-cad-suite`, `export PATH` for child processes; tools in recipes **only via full-path variables** (`$(VERILATOR)`, `$(YOSYS)`, `$(NEXTPNR)`, `$(GOWIN_PACK)`, `$(OPENFPGALOADER)`, `$(GTKWAVE)`). The Makefile has no flash-backup check.

Agent guards (`.claude/`, changed only by user request):
- `.claude/hooks/guard-flash.sh` blocks every flash write or erase (`make … flash-perm`; `openFPGALoader` with `-f` outside `--detect`, `--write-flash`, `--bulk-erase`, `--protect-flash`, `--unprotect-flash`) while `backup/tangnano9k_flash_backup.fs` (path set in the hook) is missing or empty. It runs only for the agent's Bash calls; `make`, VS Code tasks and the user's terminal are not affected. This is the only flash-backup check in the project.
- `.claude/settings.json`: board commands run outside the sandbox and always ask; credentials and shell configs are denied.

## Board

Pins: `templates/tangnano9k.cst` (all 11 on-board I/Os), generated by script with cross-checks from `YosysHQ/apicula` `examples/tangnano9k.cst` and `sipeed/TangNano-9K-example` (`led/src/9K_LED_project.cst`, `led/src/LED.v`, `uart/src/top.cst`; fetched 2026-10-15) — never edit pins by hand. LEDs, buttons and `clk` verified on hardware; UART pins (17, 18) from sources only.

| Item | Value |
| --- | --- |
| FPGA | GW1NR-LV9QN88PC6/I5 (GW1N-9C); on-chip configuration flash, 64 Mbit PSRAM in package |
| nextpnr / gowin_pack | `--device GW1NR-LV9QN88PC6/I5 --vopt family=GW1N-9C --vopt cst=<file>.cst` / `-d GW1N-9C` |
| openFPGALoader | `-b tangnano9k`; idcode `0x100481b` (GW1N(R)-9C), irlength 8, JTAG 6 MHz |
| USB | BL702 emulating FT2232 (`0403:6010`, "SIPEED JTAG Debugger"): JTAG + UART; works on macOS without drivers |
| Buttons | `btn_n[0]` (pin 3) = S2, `btn_n[1]` (pin 4) = S1; active low |
| LEDs | active low; `led[0]` (pin 10) is at the S1 end of the row |
| On-chip flash | configuration, loaded at power-on. openFPGALoader 1.1.1 writes it (`-f`: full erase, write, CRC check); cannot detect or read it; `--verify` prints `writing verification not supported` (checked in `src/gowin.cpp`) |
| External SPI flash | PUYA P25Q32H, 32 Mbit (4 MiB), JEDEC `0x856016`; user data, not configuration. `--dump-flash` reads this one at ≈ 330 B/s (full dump ≈ 3.5 h) |

## Flash backup (decided 2026-10-15)

- The on-chip flash cannot be read with openFPGALoader (no readback in `src/gowin.cpp`; release 1.1.1 is the latest).
- `backup/tangnano9k_flash_backup.fs` = Sipeed `picotiny/picotiny.fs` from `sipeed/TangNano-9K-example`: 3 557 149 B, git blob `6c01e009032a75c525c3999b66fd4cb606c2f4a0`, SHA-256 `5a9558e4b0ad2dad2812ad90757bfe6a27f6367992bf536a3304bc948a41659e`, header `GW1NR-LV9QN88PC6/I5`. That it is the actual factory image is likely (the external flash starts with RISC-V code, as picotiny's XIP firmware would) but not confirmed: the factory behaviour was not recorded before the first flash write.
- `backup/` is git-ignored: in a fresh clone, re-fetch the file and check the git blob hash.
- Restore (no make target, separate approval): `openFPGALoader -b tangnano9k -f backup/tangnano9k_flash_backup.fs`.
- The external SPI flash was not dumped (user decision: ≈ 3.5 h). Nothing in this project writes it; never use `--external-flash` without a new user decision.

## Structure

```
Makefile                 all targets; DEMO=<name> selects the design (default blinky)
Makefile.sim             generic cocotb runner, called by make sim
demo/<name>/             design: *.sv, *.cst, test_*.py, demo.mk
  blinky/                binary counter on the 6 LEDs, S1 (pin 4) = reset
  btn_counter/           6-bit counter: S2 (pin 3) = +1, S1 (pin 4) = -1, both = 0
templates/tangnano9k.cst full on-board I/O template (clk, 6 LEDs, 2 buttons, UART)
README.md                user guide (EN + UK): setup, make targets, direct tool commands, board I/O, flash
FPGA_INTRO.md            FPGA introduction for beginners (EN + UK)
tools.lock               pinned toolchain: archive, URL, SHA-256, tool versions (tracked in git)
scripts/check_tools.sh   used by make check-tools
.vscode/                 settings.json, tasks.json (DEMO picker), extensions.json
.tools/oss-cad-suite/    OSS CAD Suite darwin-arm64 (yosys, nextpnr-himbaechel, apycula/gowin_pack, iverilog, verilator, cocotb, gtkwave, openFPGALoader)
downloads/               OSS CAD Suite archive
backup/                  tangnano9k_flash_backup.fs (see "Flash backup")
build/<name>/            build and simulation output (<TOP>.fs, logs, sim_build/<TOP>.fst, results.xml)
```

`demo.mk`: `TOP`, `SOURCES` (relative, submodules before the top), `CST`, `TEST` (cocotb module without `.py`), `SIM_PARAMS` (`PARAM=value`, simulation only). Name each `.sv` file after its module (the VS Code linter finds submodules by file name).

## Toolchain

- **`tools.lock` (tracked in git) is the single source of truth**: archive name, URL, size, SHA-256 and the version strings the installed tools print. `.tools/` and `downloads/` are git-ignored and disposable; the `README.md` setup steps rebuild them and read their values from `tools.lock`.
- Currently OSS CAD Suite `2026-09-19`. Upgrade only after agreeing with the user; an upgrade changes `tools.lock` (all fields), the reference results in "Status", and nothing in `README.md`.
- Do not copy values from `tools.lock` into other files; read them (`awk '$1=="sha256"{print $3}' tools.lock`). Never put tool metadata inside `.tools/`.

## Known pitfalls

### Agent environment

- Start the Claude session in this folder: from another folder `.claude/settings.json` is not loaded, board commands run inside the sandbox and fail with `device not found`.
- `.claude/hooks/guard-flash.sh` must be executable (`chmod +x`), otherwise the hook fails as a non-blocking error and guards nothing.
- `openFPGALoader` is not on the shell `PATH` (only the Makefile sets it); direct commands use `.tools/oss-cad-suite/bin/openFPGALoader` (covered by the `*/openFPGALoader *` rules).
- Sandboxed Bash cannot write to `.vscode/` or `.claude/`; use the file-writing tool for `.vscode/`.
- OSS CAD Suite tools try to create `~/.config/yosyshq` and `~/.local/share/yosyshq`; in the sandbox this prints `Operation not permitted` without affecting results. `xcrun_db ... Operation not permitted` is noise too.

### Tools and HDL

- macOS GNU Make 3.81: use full tool paths in recipes (it looks up a simple recipe's program in the old `PATH`).
- A comment on the same line as a make variable value breaks the value.
- `Makefile.sim` gets its values as `DEMO_*`; a command-line `COMPILE_ARGS` would override cocotb's `+=`.
- cocotb only with the OSS CAD Suite Python (`tabbypy3`, `tabbypip install`), no separate venv. Without make, use `cocotb_tools.runner` and pass `test_dir` and `results_xml` (otherwise `results.xml` lands in the design folder).
- All cocotb tests of a design share one simulation: power-on reset happens only once. Tests after the first must bring the design to a known state themselves (`btn_counter`: hold both buttons).
- Verilator `-Wall`: a register with an initial value must not use `always_ff` (IEEE 1800 forbids writing an `always_ff` variable from `initial`; a declaration initialiser gives `PROCASSINIT`). Use `initial x = '0;` with plain `always @(posedge clk)` (see `btn_counter.sv`, power-on reset).
- nextpnr-himbaechel requires a pin for **every** top-level port, else `ERROR: Unconstrained IO`. CST lines for ports not in the design are silently ignored.
- `gowin_pack` warns `Numpy/Msgspec/fastcrc is not available, performance will be degraded` — speed only; installing them needs PyPI (a new domain) and is not needed.

### Hardware

- Any openFPGALoader access to the external SPI flash (`--dump-flash`) erases SRAM first: the loaded design stops. Stopping it mid-read leaves the FPGA blank until a power cycle.
- A flash write (`-f`) erases the whole on-chip flash first; there is no read-back verification, only the CRC check and a power-cycle test.
